# Bastly production deployment

This file is intentionally free of passwords, connection strings, and other secrets.

## Locked topology

Use:

- **Frontend:** Cloudflare Worker + Static Assets
- **API:** Render
- **Database:** MongoDB Atlas
- **Transactional email:** Gmail + Google App Password
- **Videos:** YouTube Unlisted
- **Admin-managed images:** Cloudflare R2
- **DNS/custom domain:** decide with the Bastly owner before final deployment

The browser must continue calling the API through the frontend origin:

```text
Browser
  ↓
https://YOUR_FRONTEND/api/...
  ↓ Cloudflare Worker reverse proxy
https://YOUR_RENDER_API/api/...
```

This is deliberate. It keeps Bastly's HttpOnly session cookie first-party/same-origin from the
browser's point of view and preserves the production Origin guard.

The browser application must not switch to a direct `https://YOUR_RENDER_API/api` base URL.

## 1. Current pre-deployment state

The frontend migration has been validated locally with:

```text
Node 22.x
npm run build
npm run check --prefix server
npm run cf:dry-run --prefix client
npm run cf:dev --prefix client -- --port 8787
```

Verified Cloudflare behavior:

- public static HTML shells resolve normally
- `/about` and `/contact` redirect to `/`
- private/auth hard-refresh routes receive `private.html`
- unknown HTML navigations also receive `private.html`
- private/unknown SPA shells send `Cache-Control: private, no-store, max-age=0`
- private/unknown SPA shells send `X-Robots-Tag: noindex, nofollow`
- missing static assets return a real `404`
- `sw.js` keeps its no-cache policy and `Service-Worker-Allowed: /`
- `/api/*` is intercepted by the Worker
- Wrangler sees only the `ASSETS` binding while `BACKEND_URL` is intentionally absent

Nothing in this section means production has been deployed yet.

### Render production environment variables

Set these in Render. Do NOT put values in Git:

```text
NODE_ENV=production

CLIENT_URL=https://FINAL_FRONTEND_ORIGIN

MONGODB_URI=<production Atlas connection string>

JWT_SECRET=<long random secret, minimum 32 characters>

REQUIRE_EMAIL_VERIFICATION=true

GMAIL_USER=<Bastly Gmail account>
GMAIL_APP_PASSWORD=<Google App Password>
EMAIL_FROM_NAME=Bastly Academy

CLOUDFLARE_R2_ACCOUNT_ID=<R2 account id>
CLOUDFLARE_R2_ACCESS_KEY_ID=<R2 access key>
CLOUDFLARE_R2_SECRET_ACCESS_KEY=<R2 secret>
CLOUDFLARE_R2_BUCKET=bastly-media
CLOUDFLARE_R2_PUBLIC_BASE_URL=<final public R2 media origin>
```

Render injects `PORT`; do not hardcode a production port.

When the Render Blueprint is used, `JWT_SECRET` is generated by Render. If the service is created
manually, generate a secret with:

```text
npm run generate:jwt
```

### Health check

After Render deploys, visit:

```text
https://YOUR_RENDER_API/api/health
```

Expected healthy shape:

```json
{
  "status": "ok",
  "service": "bastly-api",
  "database": "connected"
}
```

A disconnected MongoDB returns HTTP `503`, which lets Render detect an unhealthy API.

## 4. Cloudflare frontend

The frontend is configured by:

```text
/client/wrangler.jsonc
/client/worker/index.js
/client/public/_headers
/client/public/_redirects
```

The old Vercel configuration has been removed.

Current Cloudflare config intentionally keeps public platform URLs disabled until the owner/domain
decision is made:

```text
workers_dev=false
preview_urls=false
```

Do not deploy the frontend until one final production frontend origin has been selected.

### Build-time frontend variables

Production builds need:

```text
VITE_API_URL=/api

VITE_SITE_URL=https://FINAL_FRONTEND_ORIGIN

BACKEND_URL=https://YOUR_RENDER_API

VITE_BASTLY_WHATSAPP_NUMBER=<confirmed public WhatsApp digits>
VITE_BASTLY_PHONE_DISPLAY=<confirmed display phone>
VITE_BASTLY_INSTAGRAM_URL=<confirmed Bastly Instagram URL>
```

`BACKEND_URL` does not need `/api`.

Do not prefix `BACKEND_URL` with `VITE_`.

`BACKEND_URL` is used during the production build for public Doctor/Course SEO discovery.

### Cloudflare Worker runtime variable

The deployed Worker also needs:

```text
BACKEND_URL=https://YOUR_RENDER_API
```

This is the upstream origin used by `/api/*`.

For local Worker testing, copy:

```text
client/.dev.vars.example
```

to:

```text
client/.dev.vars
```

and set `BACKEND_URL` only after the Render API exists.

`client/.dev.vars` is ignored by Git.

### Why `/api` stays relative

Bastly's browser client defaults to:

```text
/api
```

Local Vite proxies it to port `5000`.

The production Cloudflare Worker proxies it to Render.

This gives the browser one frontend origin for both the UI and session-cookie requests.

## 5. Production build contract

A normal local build remains:

```text
npm run build
```

It is intentionally allowed to run without owner production secrets.

The strict production frontend build is explicit:

```text
npm run build:production --prefix client
```

or from `client`:

```text
npm run build:production
```

The strict production build requires:

- HTTPS `VITE_SITE_URL`
- HTTPS `BACKEND_URL`
- same-origin `VITE_API_URL=/api` when explicitly set
- confirmed public business/contact values
- no known secret accidentally exposed under a `VITE_` name
- reachable Render public API for Doctor/Course SEO discovery

The production build must fail rather than silently ship incomplete dynamic SEO shells.

## 6. Static SEO and SPA routing

The build generates public HTML head shells for:

```text
/
/faq
/privacy
/terms
/courses
/doctors
/courses/:published-slug
/doctors/:published-slug
```

`/about` and `/contact` are no longer standalone public pages. Cloudflare redirects both to `/`.

Private/auth/application routes use:

```text
private.html
```

with:

```text
Cache-Control: private, no-store, max-age=0
X-Robots-Tag: noindex, nofollow
```

This includes the known login/recovery/invite/dashboard routes.

Unknown HTML navigations also receive `private.html` so the SPA can render its own Not Found page
without initially receiving the indexable public homepage shell.

Missing static files still return a real HTTP `404`.

The build also generates:

```text
404.html
robots.txt
sitemap.xml
```

Local builds or builds without a non-local canonical URL remain `noindex`.

## 7. Caching and PWA behavior

Cloudflare headers preserve the intended policies:

```text
/assets/*          public, max-age=31536000, immutable
/brand/*           public, max-age=86400, must-revalidate
/sw.js             no-cache, no-store, must-revalidate
/site.webmanifest  public, max-age=0, must-revalidate
/offline.html      public, max-age=0, must-revalidate + noindex
/private.html      private, no-store, max-age=0 + noindex
```

The service worker continues to:

- register only on the canonical production origin
- ignore `/api`
- use network-first navigation handling
- fall back to `offline.html`
- avoid caching authenticated API responses

Do not change `VITE_SITE_URL` casually after launch because the PWA registration guard and SEO
canonicals both use the canonical frontend origin.

## 11. Cloudflare R2 media storage

Before production launch, Bastly needs a Cloudflare R2 bucket for Admin-managed images.

Required Render/server variables:

```text
CLOUDFLARE_R2_ACCOUNT_ID=
CLOUDFLARE_R2_ACCESS_KEY_ID=
CLOUDFLARE_R2_SECRET_ACCESS_KEY=
CLOUDFLARE_R2_BUCKET=bastly-media
CLOUDFLARE_R2_PUBLIC_BASE_URL=
```

The R2 access key and secret remain server-only.

The browser never uploads the original source file to Render. It creates predefined WebP variants
locally and PUTs them directly to R2 through short-lived presigned URLs generated by the Bastly API.

The bucket must allow browser `PUT` requests from the final Bastly frontend origin through an
explicit R2 CORS policy. See `R2_MEDIA_SETUP.md` for the exact flow and CORS template.

If Bastly receives a custom domain, a media subdomain such as:

```text
https://media.YOUR_DOMAIN
```

is preferred for the final public R2 media origin.
